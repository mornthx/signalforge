## What V0.2 gives you

1. **Screenshot capture from inside the production binary**:
   - `--capture-screenshot-after-ms <N> --capture-screenshot-path <png>`:
     full `MainWindow` PNG via `QWidget::grab()` (mechanism C).
   - `--capture-fullscreen-after-ms <N> --capture-fullscreen-path <png>`:
     full xvfb / X screen via `QScreen::grabWindow(0)`
     (mechanism B — includes top-level windows outside
     `MainWindow` like menu popups + modal dialogs).
2. **State-driving CLI flags** that exercise production code
   paths (not fixture-mocks):
   - Fixture loading: `--auto-load-test-fixture <yaml>`,
     `--auto-no-connect <yaml>`.
   - Connection state: signal selection via
     `--auto-select-signal <id>`; multi-driver via fixtures
     `m15_multi_2.yaml` / `m15_multi_5.yaml`.
   - Replay: `--auto-load-replay <sfreplay>` +
     `--auto-replay-play-after-ms <N>` +
     `--auto-replay-seek-percent <0-100>`.
   - Menus: `--auto-open-menu <File|Connections|Session>`.
   - Dialogs: `--auto-open-dialog <add|edit>` +
     `--auto-open-dialog-driver <serial|tcp|udp|replay>`.
   - Charts: `--auto-add-charts <n>` (V0.3-blocked on
     `rebuildChartWidgets` segfault — primitive ready for
     re-test once chart-host redesign lands).
3. **Pixel-diff regression gate** (CI):
   `tests/visual/lib/compare.py` — stdlib-only PNG decoder +
   per-channel-tolerance diff. CI uses 5 % threshold by
   default; state 13 (multi-5-drivers) uses 7.5 %.
4. **Vision-LLM semantic gate** (local + CC sessions):
   `tests/visual/lib/describe.py` returns either a structured
   JSON description (via operator-local MiMo API when
   `SF_VISUAL_DESCRIBE_BACKEND=mimo` + `MIMO_API_KEY` are set)
   or `None` (CI default; pixel-diff carries the gate).
   CC's multimodal Read tool is the primary interactive
   vision backend.
5. **Capture orchestrator**: `tests/visual/scripts/capture_baselines.py`
   captures the 20 V0.2-feasible states (12 production-
   fidelity + 8 R7 fixture-mocks for V0.3 reference) into
   `tests/screenshots/baseline-candidate/`.
6. **Operator acceptance workflow**: `scripts/accept-baseline.sh
   <state>` promotes a candidate PNG to the committed baseline
   at `tests/visual/baselines/<state>.png`.

## Acceptance rubric (R7 production-fidelity)

A captured PNG qualifies as a V0.2 production-fidelity
baseline only if **the GUI state shown is reachable through
production code paths without test-only state mutation**. Test
infrastructure that:

- inlines `setText` from a production slot (e.g.
  `autoStartRecording` after R6 now sets `recordingStatusLabel_`
  to mirror `onRecordToggle`); OR
- fabricates a string the production GUI never emits (e.g.
  R6's `seek N %%` in `autoReplaySeekPercent`); OR
- bypasses a user-action event source (e.g. R5's `showPopup()`
  direct call instead of a Qt mouse press)

… produces a (d) **fixture-mock** capture. It works as test-
infrastructure documentation; it does NOT serve as a V0.2
production-fidelity baseline.

For V0.3 redesign A/B comparison: only the **12 production-
fidelity baselines** (00, 02, 04, 12, 13, 24, 25, 26, 30, 31,
32, 33) are valid measurement references at V0.2 close.

## End-to-end perception loop (the S6 demo, generalised)

For any change suspected to affect the GUI:

```bash
# 1. Build the candidate change.
cmake --build --preset debug

# 2. Run the visual ctest. PASSES at the 5 % gate do not
#    mean "no regression" — they mean "no regression the
#    pixel-diff can see".
xvfb-run --auto-servernum ctest --preset debug -L visual --output-on-failure

# 3. For any baseline that the change might touch, inspect
#    the captured PNG via CC's Read tool (or any image viewer
#    + MiMo API if SF_VISUAL_DESCRIBE_BACKEND=mimo is set).
#
#    From inside a CC session:
#       Read tests/screenshots/<state>.png
#
#    Compare against the operator-approved committed baseline:
#       Read tests/visual/baselines/<state>.png
#
#    Narrate what changed semantically. If the change is
#    intended, accept the new baseline.
#    If the change is unintended, diagnose + fix.

# 4. If the change is intended (UI redesign / new feature):
scripts/accept-baseline.sh <state>            # default: tests/screenshots/baseline-candidate/
scripts/accept-baseline.sh <state> ""         # tests/screenshots/<state>.png  (visual-test path)

git diff --staged                              # review the staged baseline change
git commit -m "<state>: <human-readable visual change>"
```

For new visual tests (V0.3+): follow the pattern in
`tests/visual/README.md` §"Adding a new visual test".

## CI integration (S5)

`.github/workflows/ci.yml` uploads `tests/screenshots/**` as
the `visual-screenshots-<preset>` artifact (14-day retention)
on every CI run, regardless of test pass/fail
(`if: always()`). When a CI visual test fails:

1. Download the artifact: `gh run download <run-id> -n visual-screenshots-debug`.
2. Diff each captured PNG against the committed baseline:
   - CC's Read tool side-by-side.
   - Or:
     ```python
     from lib.compare import compare_baseline
     compare_baseline("captured.png", "tests/visual/baselines/<state>.png",
                      max_diff_percent=5.0)
     ```
3. If intended → `scripts/accept-baseline.sh` per state →
   commit + push.
4. If unintended → diagnose via Read tool + grep + propose fix.

**Public-repo security (HALT trigger H7)**: CI runs no vision
LLM. Zero `secrets.*` references to API keys in any workflow.
Vision-LLM verdicts are local-only. CI gate is pixel-diff only.

## Cross-environment baseline pinning (V0.3 follow-up)

M15 close surfaced a cross-environment style drift: local
xvfb renders Qt widgets with a stripped-down style (mostly
white, no inter-component fills) while CI's Ubuntu-24.04
xvfb renders the canonical Qt-default style. Pixel-diff:
14–33 % depending on widget density.

Both renderings are functionally correct — same widgets,
same labels, same state. The drift is style-level, not
semantic.

**V0.2 workaround**: baselines committed reflect one
environment's rendering; the other shows ~15 % diff on a
fresh local run. CC's Read tool sees through the style
drift to confirm semantic equivalence.

**V0.3 fix** (M16 design tokens): pin Qt style + fontconfig
identically in both local-dev and CI:

```yaml
# .github/workflows/ci.yml  (V0.3)
- name: Pin Qt style + fonts
  run: |
    sudo apt-get install -y \
        fonts-dejavu-core fonts-liberation
    echo "QT_STYLE_OVERRIDE=Fusion" >> $GITHUB_ENV
```

Document the same in `docs/dev-setup.md` so local devs
reproduce the CI rendering. After M16 lands, V0.2's baselines
need a one-time re-capture against the pinned environment.
