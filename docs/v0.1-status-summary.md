## 2. Architectural assessment (carried from prior scope eval)

### 2.1 Is the V0 backend ship-stable?

**Yes.** Multi-layer evidence:

- **Live-mode chain** (Connection → PipelineManager.attach
  → DecoderRegistrar.onPipelineAttached → SchemaDecoder
  → SignalValueSink fan-out via TeeSink → SignalBufferRegistry
  + SessionWriter) end-to-end exercised by
  `tests/integration/test_v1_live_mode_pipeline.cpp` + S1 smoke
  + operator dogfood.
- **Recording chain** (TeeSink-routed; SessionWriter
  always-subscribed at MainWindow ctor; signal catalog
  cached on `onSignalsRegistered`) produces clean SFREPLAY v1
  files on the natural Connect → Record flow (Wave 2 F6 fix).
- **Replay chain** scrub/step/play-pause + speed change with
  re-anchor (Wave 4 F19) + state guard (Wave 4 F14).
- **Persistence** `~/.config/signalforge/connections.yaml`
  written on every mutation + `aboutToQuit` belt-and-suspenders
  (ADR-013).

### 2.2 Is the GUI architecture viable for V0.3 rebuild?

**Conditional yes** — the QQuickWidget + QQuickItem hosting
pattern (ADR-001 + ADR-010 + ADR-011) carried five layered
release-prereq fixes through M13/M14. The integration glue
hardened by ADR-008 → ADR-013 stays reusable for V0.3. Whether
V0.3 keeps this hosting pattern or switches to a different one
is a V0.3 design decision — informed by V0.2 vision-infrastructure
findings.

### 2.3 Frozen-surface impact

**0 / 2.** All M14 fixes lived in non-frozen `.cpp` /
non-frozen `main_window.{hpp,cpp}` (V1 integration point;
intentionally unfrozen per M9 / M11 / M13 precedent).
M2–M12 frozen `.hpp` files sha256-audit-clean across the
M13/M14 cycle. Per V0 charter §3, the same freeze applies to
V0.2 and V0.3.

## 6. V0 governance lessons (consolidated, M0 → M14)

The M13 + M14 release-prereq cycle surfaced a consistent
multi-milestone gap pattern. Per V0 charter §1, the **root cause**
is that AI advisor + CC do not see the actual GUI; the operator's
binary pass/fail report cannot convey visual UX issues. M0–M14
built solid backend on the assumption that "functional plumbing
== ship-ready" but real users need visual + interaction quality
in addition to plumbing.

### 6.1 V0.1 lessons captured

- **Per-test binary link topology ≠ release-binary link
  topology.** ADR-010 §Implementation lesson: every
  `Q_INIT_RESOURCE` / `qmlRegisterType` /
  `qRegisterMetaType` registration in a static archive
  needs an explicit symbol reference, or `nm $bin | grep
  $symbol` must smoke it.
- **Frozen-surface protocol works.** All M2–M12 frozen `.hpp`
  files unchanged across the M13/M14 cycle. ADR-008's
  additive `setSchemaForDriverType` is the correct
  frozen-surface escape hatch pattern.
- **CI release-binary smoke required.** M14 S1 catches scene-
  graph + qrc + chart-sizing regressions automatically.
  V0.x extensions close the remaining audit gaps.
- **Operator + CC daily ping-pong cadence works** for finding
  bugs reactively. V0.2 vision infrastructure replaces it
  with proactive screenshot-based perception.
- **Honest scope reduction beats brittle automation.** M14
  S6 mechanical-18 scaffold ships with 1 of 8 tests
  automated + the rest documented as V0.x candidates.
  Forcing automation under xvfb's readyRead quirks would
  mean faking it rather than fixing the underlying
  `UdpDriver::onReadyRead` race in V0.x.

### 6.2 Lessons V0.2+ inherits

- **AI must see the GUI** to validate it. The decision
  loop (GUI → operator perception → verbal report → CC
  inference → advisor decision) loses too much information
  to detect visual UX defects. M15 builds the screenshot
  capture + vision LLM integration that closes this loop.
- **Quality > schedule.** V0 charter §8 rewords V1 spec §1
  ("Reality > schedule") and now governs without exception.
