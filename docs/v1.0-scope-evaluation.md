## 2. Architectural assessment

### 2.1 Is the V1 GUI architecture ship-ready?

**YES.** Multi-layer evidence:

- **Chart-rendering pipeline** (QQuickWidget host scene +
  QQuickItem chart with explicit geometry binding +
  Q_INIT_RESOURCE for static-archive qrc retention) works
  in real X11 (run-5 operator confirmation). Software-RHI
  rasterization under xvfb does have a known limitation
  for 1-px line strips, addressed by the smoke harness's
  env-gated `QSGSimpleRectNode` canary — not a production
  defect.
- **Live-mode chain** (Connection state → PipelineManager
  attach → DecoderRegistrar onPipelineAttached →
  SchemaDecoder construction → SignalValueSink fan-out via
  TeeSink → SignalBufferRegistry + SessionWriter) is now
  exercised end-to-end by `tests/integration/test_v1_live_mode_pipeline.cpp`
  + S1 smoke + operator dogfood. All 12 sub-paths in spec
  §3.2 "Live mode chain" pass.
- **Recording chain** (TeeSink-routed; SessionWriter
  always-subscribed at MainWindow ctor; signal catalog
  cached on `onSignalsRegistered` whether recording or
  not) produces clean SFREPLAY v1 files with non-zero
  Type-1 records on the natural Connect → Record flow
  (Wave 2 F6 fix).
- **Replay chain** (PlaybackController + ReplayModeManager
  + Replay toolbar) opens files, switches modes,
  scrubs/steps/play-pause, exits with the correct
  resume-or-stay-Idle decision dialog. Session-load time
  for the 24 kB / 901-record fixture is < 1 s after F15a
  idempotent re-registration (F11 closed).
- **Persistence** (`~/.config/signalforge/connections.yaml`)
  is written on every mutation + on `aboutToQuit`
  (Wave 2 F17 fix + ADR-013 belt-and-suspenders).

### 2.2 Were all Critical bugs fixable in M14?

**YES.** All 4 (F4 / F6 / F15 / F17) closed. None needed:

- New dependencies (CLAUDE.md §1)
- Frozen-`.hpp` modification (M14 HALT #5)
- Architectural rewrite of any V1 subsystem
- Spec amendment to M0-M12 specs

Each fix is a small-scope wire-up + invariant correction;
ADR-011 + ADR-013 capture the architectural rationale.

### 2.3 Are the V1 design decisions sound?

The five layered bugs caught between M13 and M14
(ADR-008 → ADR-011, ADR-013) all share the same root: per-
module unit tests verified single-subsystem semantics in
isolation, but no end-to-end integration test exercised the
GUI path until M14 S1 CI smoke + S3 operator audit. The
**design** of the components is sound; the **integration
testing surface** was incomplete pre-M14.

The M14 S1 CI smoke is now a permanent V1+ governance
asset that catches scene-graph / qrc / chart-sizing
regressions automatically. ADR-008/009/010/011/013 V1.0
governance lessons sections call for two more smoke
extensions (persistence smoke + recording smoke) — both
listed in §6 below as V1.0.1 candidates.

## 3. Three-scenario analysis

Per spec §4.3 / M14.5 X, V1.0 ships in one of three forms.
This document chooses one explicitly.

### 3.1 Scenario A — V1.0 full ship

**Choice: this is the recommended path.**

Justification:

- 7 of 7 in-scope findings resolved (F1, F4, F6, F10, F11,
  F12, F15, F17, F18). F10/F11 auto-resolved by Wave-2/3
  fixes.
- 0 Critical open. 0 Serious open (F11 closed by F15a;
  F14 / F18 either fixed or V1.0.1 deferred).
- 5 Minor V1.0.1 candidates — all cosmetic / UX-polish
  / observability; none cause data loss or data
  corruption.
- M13 18-test acceptance projection (per `m14-gui-audit-
  report.md` §"Updated M13 18-test acceptance projection"):
  16/18 best-case after Wave 3, against a ≥ 16/18 bar
  (M14 spec §5.5 / §6 HALT #4). T9 / T18 remain △ due to
  F14 V1.0.1 deferral; rest of the bar passes.
- Frozen-surface counter 0/2; HALT #5 never triggered.
- No new dependencies.

Action plan:

1. Author M14-done.md (S7).
2. Open PR `milestone/M14 → main` (per M14-concerns C3).
3. Operator runs S6 18-test final verification.
4. Phase 2 (human checkpoint) approves merge + V1.0
   tag-and-release.
5. Phase 3 (CC autonomous) merges, tags `v1.0.0`, pushes
   tag, creates GitHub Release with the .deb artifact.

Risk:

- F14 (Replay-mode Open Session guard) is Serious-deferred.
  Worst case: an operator opening a second session while
  in Replay mode sees an error popup, not a crash or data
  loss. Acceptable for V1.0 ship; V1.0.1 fixes via
  `QAction::setEnabled` bound to ReplayModeManager state.
- 5 Minor V1.0.1 backlog items eat the V1.0.1 milestone
  budget. Reasonable: a single-purpose follow-up patch
  release within ~2 weeks of V1.0.

### 3.2 Scenario B — V1.0 reduced ship

**Not chosen.** Rationale:

- No V1 feature is architecturally broken to the point
  it must be deferred. Live mode, Recording, Replay,
  Connection lifecycle, Multi-chart UI, Persistence,
  Mode transitions all pass operator validation.
- All 4 Critical fixes are already shipped on
  `milestone/M14`; no remaining gating fix is "out of
  scope for M14".
- Reducing scope at this point would defer features
  that are demonstrably working — penalty for no
  benefit.

### 3.3 Scenario C — V1.0 cancelled, V1.5 first

**Not chosen.** Rationale:

- V1 architectural decisions are sound (§2.3 above).
  No fundamental rewrite required.
- ADR-008 → ADR-013 are integration-glue fixes, not
  architectural pivots. They preserve M2-M12 frozen
  surfaces; they document gaps the GUI audit revealed
  and the corresponding minimal plumbing fixes.
- The integration-test gap that allowed those bugs to
  reach M13 is closed by the M14 S1 CI smoke + the V1.5+
  smoke extensions (§6).
- Cancelling V1.0 would discard the entire M0-M14
  delivery pipeline (~14 milestones, ~30 weeks of work)
  for issues that fixed in 4 calendar days of M13 + M14
  cycle. Not justifiable.

## 7. V1 governance lessons (consolidated, M0 → M14)

The M13/M14 release-prereq cycle surfaced a consistent
pattern. ADR-008 / ADR-009 / ADR-010 / ADR-011 / ADR-013
all document the same root cause:

> Per-module unit tests verified single-subsystem
> semantics in isolation, but no end-to-end GUI
> integration test exercised the production path until
> M14 S1.

Specific manifestations:
- M5 §4.6 deferred decoder schema wire-up (ADR-008).
- M9 deferred PipelineManager attach plumbing (ADR-009).
- M8/V1 chart QQuickWidget hosting + qrc linking +
  geometry binding (ADR-010 + ADR-011).
- M9/M10 wire-up gaps in MainWindow's record-toggle and
  ConnectionManager's autoSave bootstrap (ADR-013).
- M6 SignalBufferRegistry idempotent re-registration
  (M14 F15 fix; no ADR — bookkeeping correctness).

### Lessons carried into V1.5+

- **CI release-binary smoke test required.** M14 S1
  produces a minimal smoke that catches scene-graph + qrc
  + chart-sizing regressions automatically. V1.5+ adds
  persistence + recording + buffer-pressure smoke
  extensions.
- **Per-test binary link topology ≠ release binary link
  topology.** ADR-010 implementation lesson: each
  `Q_INIT_RESOURCE` / `qmlRegisterType` / `qRegisterMetaType`
  registration in a static archive needs an explicit
  symbol reference, or `nm $bin | grep $symbol` must
  smoke it.
- **Frozen-surface protocol works.** M2-M12 frozen `.hpp`
  files are byte-for-byte unchanged across the M13/M14
  release-prereq cycle (sha256-audited at M13 S6 +
  reverified at S5 here). Additive ADRs (ADR-008's
  `setSchemaForDriverType` on M5-frozen) are the
  correct escape hatch.
- **18-test HW verification protocol is the gate-of-
  last-resort.** It worked: 5 operator runs caught 5
  distinct bug layers. But it's slow + expensive. M14
  S1 CI smoke pushes that detection earlier in the
  feedback loop.
- **Phase 4 review template should include "items
  deferred from prior milestones".** M0-M12 spec writers
  did not always enumerate the integration plumbing
  expected of MainWindow; deferrals accumulated into
  M13/M14. V1.5+ specs should explicitly list every
  caller-driven wire-up the milestone introduces.
- **Operator + CC pairing cadence works.** M14-concerns
  C2 daily ping-pong by spec §3.2 section was the
  fastest path through 14 audit findings. V1.5+
  milestones with audit phases should reuse the
  template.
